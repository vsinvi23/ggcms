# LLM Tool Calling: Wiring APIs and JSON Function Definitions

### The Problem: Parsing Hell in Multi-Agent Systems
Before 2023, giving tools to Large Language Models required intense "prompt engineering" to coerce the model into outputting specific text formats (e.g., `Action: GET /users/123`). Developers had to write fragile RegEx parsers to extract the API names and arguments. If the LLM missed a quote or hallucinated a parameter, the whole pipeline crashed.

Modern LLMs solve this with **Native Tool Calling (Function Calling)**. The model is fine-tuned to recognize a JSON Schema definition of a function, and when appropriate, it outputs a guaranteed, perfectly structured JSON object representing the function call instead of standard conversational text.

### How Tool Calling Works Under the Hood
1. **Definition**: The developer passes an array of JSON Schemas (describing the available APIs) to the LLM alongside the user prompt.
2. **Trigger**: The LLM decides if it needs data to answer the prompt. If yes, it stops generating text and yields a `tool_call` object.
3. **Execution**: The host application intercepts the `tool_call`, parses the JSON arguments, runs the local Python/Node code, and captures the result.
4. **Resolution**: The host sends the result back to the LLM as a `tool_result` message. The LLM consumes this data and formulates the final answer.

```text
+-------------------------------------------------------------+
|               The Tool Calling Handshake                    |
+-------------------------------------------------------------+
| 1. App -> LLM:  Messages + [JSON Schemas]                   |
| 2. LLM -> App:  "call_function": {"name": "get_weather",    |
|                                   "args": {"city": "SFO"}}  |
| 3. App (Local): executes get_weather("SFO") -> 22°C         |
| 4. App -> LLM:  "tool_result": "22°C"                       |
| 5. LLM -> App:  "It is currently 22 degrees in SFO."        |
+-------------------------------------------------------------+
```

### Defining Tools with JSON Schema & Pydantic
LLM APIs (OpenAI, Anthropic, Gemini) expect tools to be defined using strict JSON Schema format. Writing raw JSON Schema is error-prone. The industry standard in Python is to use **Pydantic** to define data models, which dynamically generate the JSON Schema.

#### Example: Raw JSON Schema vs Pydantic
Here is the raw JSON Schema expected by an LLM for a weather tool:
```json
{
  "name": "get_weather",
  "description": "Get the current weather for a location",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "City and state, e.g. San Francisco, CA"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"]
      }
    },
    "required": ["location"]
  }
}
```

Instead of managing giant JSON blobs, robust AI engineering uses Pydantic to bridge Python types and LLM schemas:

```python
from pydantic import BaseModel, Field
import json

class WeatherInput(BaseModel):
    location: str = Field(..., description="City and state, e.g. San Francisco, CA")
    unit: str = Field(default="celsius", description="Temperature unit")

def get_weather(location: str, unit: str = "celsius") -> str:
    # Simulated API call
    return f"22 {unit} in {location}"

# Generate the JSON Schema dynamically
schema = {
    "name": "get_weather",
    "description": "Get the current weather for a location",
    "parameters": WeatherInput.model_json_schema()
}

print(json.dumps(schema, indent=2))
```

### Handling the Tool Execution Loop
When the LLM triggers a tool, the payload must be parsed, validated, and executed securely. 

```python
import json

def process_llm_response(llm_response_message):
    # Check if the LLM decided to call a tool
    if getattr(llm_response_message, "tool_calls", None):
        for tool_call in llm_response_message.tool_calls:
            function_name = tool_call.function.name
            
            # Safely load the JSON arguments
            try:
                raw_args = json.loads(tool_call.function.arguments)
            except json.JSONDecodeError:
                return trigger_error_recovery("Invalid JSON generated by LLM")
            
            # Map string name to actual Python function
            if function_name == "get_weather":

                try:
                    validated_args = WeatherInput(**raw_args)
                    result = get_weather(
                        location=validated_args.location,

                except Exception as e:
                    # Pass validation errors back to LLM to self-correct

```

### Best Practices for Tool Defintions
1. **Semantic Descriptions**: The LLM relies entirely on the `description` fields to know *when* to use a tool. Be extremely descriptive. Instead of "Fetch data," use "Fetches customer billing history using an email address."
2. **Enums Over Strings**: Whenever possible, restrict inputs using Enums (e.g., `["USD", "EUR"]`). This mathematically prevents the LLM from hallucinating invalid configurations.
3. **Error Feeding**: If a tool fails (e.g., 404 Not Found, or validation error), send the exact error trace back in the `tool_result`. Modern LLMs will read the error and try calling the tool again with corrected arguments.

### Conclusion
Native tool calling has shifted AI engineering from parsing text with RegEx to building robust, type-safe API routers. By leveraging Pydantic and JSON Schema, developers can grant LLMs safe, deterministic read/write access to databases, web APIs, and local filesystems.
