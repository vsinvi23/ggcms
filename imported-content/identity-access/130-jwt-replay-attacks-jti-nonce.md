# Mitigating JWT Replay Attacks: Enforcing JTI and Nonces

## The Problem: The Stateless Liability of JSON Web Tokens
JSON Web Tokens (JWTs) are widely celebrated for enabling stateless authentication. Because a Resource Server (RS) can verify a JWT entirely by checking its cryptographic signature and expiration claim (`exp`), it does not need to query a central database for every incoming request. However, this stateless nature introduces a severe security vulnerability: JWT replay attacks. 

If an attacker intercepts a valid JWT (through transport layer exposure, cross-site scripting, or logging leakage), they can repeatedly replay that token against target APIs until the token reaches its expiration time. Even if the original user logs out, the intercepted JWT remains perfectly valid in the eyes of the resource server. Because the server does not maintain session state, it cannot inherently distinguish between a legitimate client request and an attacker replaying a stolen token. For high-value transactions—such as financial transfers or administrative actions—relying solely on standard JWT expiration is an unacceptable security risk.

## The Mental Model: Dynamic Uniqueness Verification
To defend against replay attacks without abandoning the benefits of JWTs, we must introduce mechanisms that enforce token uniqueness. We do this by transitioning from purely stateless validation to "hybrid validation" using two claims defined in RFC 7519:
1. **`jti` (JWT ID):** A globally unique identifier for the token. Once the Resource Server accepts a token with a specific `jti`, that ID is logged in a fast, distributed blocklist. If the same `jti` is presented again before its original expiration, it is rejected.
2. **`nonce`:** A cryptographic "number used once" generated by the client or authorization server. The recipient ensures that the token contains the matching, expected nonce.

```
 Client                          Resource Server                    Redis Cache
   |                                    |                                |
   |--- 1. Send Request + JWT(jti) ---->|                                |
   |                                    |--- 2. Query jti in Cache ----->|
   |                                    |<-- 3. jti Not Found (OK) ------|
   |                                    |                                |
   |                                    |--- 4. Store jti + TTL (exp) -->|
   |                                    |                                |
   |<-- 5. Authorized Response ---------|                                |
   |                                    |                                |
   |--- 6. Replay Same JWT(jti) ------->|                                |
   |                                    |--- 7. Query jti in Cache ----->|
   |                                    |<-- 8. jti Found (EXISTS) ------|
   |                                    |                                |
   |<-- 9. HTTP 401 Unauthorized -------|                                |
```

Because storing every active `jti` indefinitely would exhaust storage, the Resource Server only tracks the `jti` for the duration of the JWT's lifespan. Once the token's `exp` is reached, it is naturally invalid, allowing the server to clean up the cached `jti` entry.

## Technical Attack Vectors and Scenarios
1. **Man-In-The-Middle Interception:** Transport-level sniffing on insecure Wi-Fi or misconfigured proxies can expose JWTs in headers.
2. **API Gateway Log Leakage:** Enterprise logging systems or APMs sometimes dump request headers, storing raw authorization bearer tokens in plaintext logs.
3. **Cross-Site Scripting (XSS):** If tokens are stored in `localStorage`, XSS payloads can extract and exfiltrate them.

## Implementing JTI Tracking with Redis and Node.js
Below is a highly performant implementation of a Node.js Express middleware that validates the `jti` claim using Redis to prevent replay attacks.

```javascript
const redis = require('redis');
const jwt = require('jsonwebtoken');
const redisClient = redis.createClient({ url: 'redis://localhost:6379' });

redisClient.connect().catch(console.error);

async function preventJWTReplay(req, res, next) {
    const authHeader = req.headers.authorization;
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
        return res.status(401).json({ error: 'Missing token' });
    }

    const token = authHeader.split(' ')[1];

    try {
        // Perform standard signature and expiration validation
        const decoded = jwt.verify(token, process.env.JWT_PUBLIC_KEY, {
            algorithms: ['RS256']
        });

        const jti = decoded.jti;
        const exp = decoded.exp;

        if (!jti) {
            return res.status(400).json({ error: 'Missing JTI claim' });
        }

        // Calculate Remaining Time-To-Live (TTL) in seconds
        const currentTime = Math.floor(Date.now() / 1000);
        const ttl = exp - currentTime;

        if (ttl <= 0) {
            return res.status(401).json({ error: 'Token expired' });
        }

        // Set NX: Only set key if it does not exist (Atomic operations)
        const isUnique = await redisClient.set(`jti:${jti}`, 'used', {
            EX: ttl,
            NX: true
        });

        if (!isUnique) {
            return res.status(401).json({ error: 'Token has already been used (Replay attack detected)' });
        }

        req.user = decoded;
        next();
    } catch (err) {
        return res.status(401).json({ error: 'Invalid token' });
    }
}
```

## Hardening Recommendations
1. **Short Token Lifespans:** Limit access token lifetime to 15 minutes or less to minimize the cache storage footprint of `jti` tracking.
2. **Enforce Cryptographic Nonces in OpenID Connect:** In client-side single page applications (SPAs), always generate a cryptographically secure random `nonce` before initiating the OIDC flow, store it locally, and match it against the `nonce` claim in the returned ID token.

By enforcing dynamic `jti` checking against an atomic distributed store and requiring OIDC nonces, engineering teams can eliminate the stateless vulnerability of JWTs and secure high-risk transactional APIs from replay exploits.
