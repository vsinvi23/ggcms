# OAuth Actors Explained: Core Architecture Roles

To design, implement, or troubleshoot an OAuth 2.0 implementation, you must move beyond abstract definitions of "apps" and "servers" and adopt the precise, standard terminology defined in RFC 6749.

OAuth 2.0 explicitly defines four distinct actors (roles) that interact to achieve delegated authorization. Let's break down each actor's technical responsibilities, trust boundaries, and threat profiles, and then see them in action.

---

## The Four Core Actors

```
                 +----------------------------------------+
                 |          Resource Owner (User)         |
                 +-------------------+--------------------+
                                     |
                         Authenticates & Grants
                                 Consent
                                     |
                                     v
+------------------+     Redirects via Browser     +------------------------+
|                  |==============================>|                        |
|                  |                               |  Authorization Server  |
|      Client      |       Exchanges Auth Code     |  (Issues Tokens & keys)|
| (Third-Party App)|<=============================>|                        |
|                  |                               +------------------------+
+--------+---------+
         |
    Requests API
    with Access Token
         |
         v
+------------------+
| Resource Server  |
|  (APIs & Data)   |
+------------------+
```

---

## 1. The Resource Owner (The User)
The **Resource Owner** is the human or entity that owns the data and has the authority to grant access to it.
- **Responsibility:** Authenticates with the Authorization Server and decides whether to approve or deny authorization requests from the Client.
- **Trust Boundary:** High-trust. The user has an established identity and credential set with the Authorization Server.
- **Threat Profile:** Phishing, social engineering, credential stuffing.

---

## 2. The Client (The Third-Party Application)
The **Client** is the application making protected resource requests on behalf of the Resource Owner.
- **Responsibility:** Initiates authorization flows, safely handles redirects, securely stores tokens, and passes tokens in API requests.
- **Classification:**
  - **Confidential Client:** An app that can securely maintain a client secret (e.g., a server-side web app running Node.js/Java/Python behind a firewall).
  - **Public Client:** An app that *cannot* protect a secret (e.g., Single Page Apps running in a browser, mobile/desktop applications).
- **Threat Profile:** Token leakage, source-code tampering, reverse engineering, unauthorized interception.

---

## 3. The Authorization Server (The Identity Provider / AS)
The **Authorization Server** is the engine that authenticates the Resource Owner, obtains authorization, and issues Access Tokens to the Client.
- **Responsibility:** Hosts login and consent endpoints, validates client identities, generates cryptographically secure codes and tokens, and manages token revocation.
- **Trust Boundary:** Root of trust. This server manages security-sensitive credentials and signs cryptographic tokens.
- **Threat Profile:** Key compromise, token database leakage, denial of service, SQL injection, open redirect exploits.

---

## 4. The Resource Server (The API Server / RS)
The **Resource Server** is the host of the protected user data (APIs).
- **Responsibility:** Accepts access tokens, validates their signatures/lifecycles, enforces scopes, and responds to authorized requests with appropriate data payloads.
- **Trust Boundary:** Med-High. It trusts the tokens generated by the Authorization Server and relies on them to make access decisions.
- **Threat Profile:** Token counterfeiting, injection attacks, data harvesting, Broken Object-Level Authorization (BOLA).

---

## Technical Actor Interaction Model

Let’s trace the actors' exact interactions using a robust, production-style Express.js backend representing the **Resource Server (RS)**. 

To demonstrate how the **Resource Server** validates tokens issued by the **Authorization Server (AS)** on behalf of the **Resource Owner (User)**, we implement JWT-based signature validation using a public key (JSON Web Key Set - JWKS).

```javascript
const express = require('express');
const axios = require('axios');
const jwt = require('jsonwebtoken');
const jwksClient = require('jwks-rsa');

const app = express();

// Set up the JWKS client to pull public verification keys from the Authorization Server (AS)
const jwksResolver = jwksClient({
  jwksUri: 'https://as.example.com/.well-known/jwks.json',
  cache: true,
  rateLimit: true,
  jwksRequestsPerMinute: 15
});

// Helper to match the key ID (kid) of the incoming JWT signature
function getVerificationKey(header, callback) {
  jwksResolver.getSigningKey(header.kid, (err, key) => {
    if (err) {
      callback(err, null);
    } else {
      const signingKey = key.getPublicKey() || key.rsaPublicKey;
      callback(null, signingKey);
    }
  });
}

// Middleware executing Resource Server (RS) responsibilities
function verifyAccessToken(requiredScope) {
  return (req, res, next) => {
    const authHeader = req.headers['authorization'];
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
      return res.status(401).json({ error: 'Missing or malformed Access Token' });
    }

    const token = authHeader.split(' ')[1];

    // RS validates token cryptographically against the AS public keys
    jwt.verify(token, getVerificationKey, {
      algorithms: ['RS256'],
      issuer: 'https://as.example.com' // AS Identity confirmation
    }, (err, decodedToken) => {
      if (err) {
        return res.status(401).json({ error: 'Invalid or expired Access Token signature' });
      }

      // RS validates scope (granted by the Resource Owner during the flow)
      const scopes = decodedToken.scope ? decodedToken.scope.split(' ') : [];
      if (!scopes.includes(requiredScope)) {
        return res.status(403).json({
          error: 'Insufficient Scope',
          message: `This action requires scope '${requiredScope}'.`
        });
      }

      // Bind the Resource Owner's user ID (subject) to the request
      req.resourceOwnerId = decodedToken.sub;
      next();
    });
  };
}

// Protected Resource Endpoint
app.get('/api/v2/user-profile', verifyAccessToken('profile:read'), (req, res) => {
  // RS serves data belonging to the Resource Owner
  res.json({
    resourceOwner: req.resourceOwnerId,
    email: 'alice@example.com',
    accountStatus: 'Active',
    authorizedClient: 'client-app-7788'
  });
});

app.listen(5000, () => console.log('Resource Server (RS) running on port 5000'));
```

## Architectural Separation of Concerns

By formalizing these four actors, OAuth enforces a clean separation of concerns:

1. **Authentication is Isolated:** The Resource Server (RS) doesn't care *how* the user authenticated (password, MFA, social login). It only cares about the resulting Access Token.
2. **Clients are Sandboxable:** If a Client behaves maliciously or gets compromised, the Authorization Server can revoke its access instantly without impacting the Resource Owner's primary account.
3. **APIs are Protected:** The Resource Server can scale out horizontally, validating cryptographically signed tokens from the AS without database lookups.
