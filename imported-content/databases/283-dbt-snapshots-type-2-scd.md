# dbt Snapshots: Designing Type 2 Slowly Changing Dimensions (SCD) for Historical Audits

## The Overwritten History Problem
Transactional databases are optimized for real-time reads and writes. To save disk space and improve application performance, they overwrite data. When a customer changes their subscription plan from "Basic" to "Premium", or a product's price is updated, the database runs an `UPDATE` statement that permanently overwrites the old value. 

In a modern data warehouse, this overwrite deletes vital context. If a data analyst runs a historical report to evaluate customer churn or sales performance over the past fiscal year, they cannot reconstruct the pricing or plan states that existed at the exact moment of each transaction. To run accurate historical audits and temporal analyses, the data warehouse must implement Type 2 Slowly Changing Dimensions (SCD Type 2), which track changes over time by creating new rows with valid start and end timestamps.

## Mental Model: Append-Only Temporal States
A dbt Snapshot implements SCD Type 2 by querying a mutable source table at regular intervals, comparing the source data with the previously snapshot-ed table, and writing the differences as an append-only historical log. 

```
Source Table: (User 1, Plan='Basic')
           | (Updated to 'Premium' at 2026-06-01)
           v
Snapshot Table (SCD Type 2):
+----+------+---------+---------------------+---------------------+
| ID | User |  Plan   |   dbt_valid_from    |    dbt_valid_to     |
+----+------+---------+---------------------+---------------------+
| 1  | 1    | Basic   | 2026-05-01 00:00:00 | 2026-06-01 10:00:00 |
| 2  | 1    | Premium | 2026-06-01 10:00:00 | NULL                |
+----+------+---------+---------------------+---------------------+
```

The active record always carries a `dbt_valid_to` of `NULL`, while past states carry the exact timestamp of their supersession.

## Deep Snapshot Mechanics and Meta-fields
To track changes, dbt adds several internal metadata fields to the snapshot table:

- `dbt_scd_id`: A unique primary key generated by hashing the source table's primary key and the record's modification time.
- `dbt_updated_at`: The timestamp when the record was last updated in the source table.
- `dbt_valid_from`: The timestamp when this historical version of the record became active.
- `dbt_valid_to`: The timestamp when this version was superseded. It is set to `NULL` for the active version.

### The Two Change-Detection Strategies
dbt provides two strategies for identifying modifications in the source table:

1. **Timestamp Strategy**: Requires a reliable update timestamp column (e.g., `updated_at`) in the source table. When dbt runs, it checks if the source table's timestamp is newer than the `dbt_updated_at` stored in the snapshot. This is the most efficient strategy.
2. **Check Strategy**: Used when the source table lacks a reliable update timestamp. dbt computes a hash of a configured list of columns (or all columns via `check_cols = 'all'`) and compares it against the existing snapshot.

### Under the Hood: The Merge Statement
When you run `dbt snapshot`, dbt compiles a complex `MERGE` statement (or an `INSERT` and `UPDATE` transaction, depending on your target data warehouse). It left-joins the source table to the active rows of the existing snapshot table.

If a match is found and the change-detection strategy indicates the row has changed:
- dbt updates the active snapshot record, setting `dbt_valid_to` to the snapshot execution runtime.
- dbt inserts a brand new row containing the updated values, setting `dbt_valid_from` to the snapshot runtime and `dbt_valid_to` to `NULL`.

## Implementation Configuration
The following configuration block demonstrates a robust dbt snapshot implementation targeting a customer accounts table:

```sql
{% snapshot customer_accounts_snapshot %}

{{
    config(
      target_database='analytics_prod',
      target_schema='snapshots',
      unique_key='account_id',
      strategy='timestamp',
      updated_at='last_modified_date',
      invalidate_hard_deletes=True
    )
}}

SELECT
    account_id,
    customer_name,
    subscription_tier,
    billing_country,
    last_modified_date
FROM {{ source('crm_raw', 'accounts') }}

{% endsnapshot %}
```

By setting `invalidate_hard_deletes=True`, dbt automatically updates the `dbt_valid_to` field of any snapshot records that are completely missing from the source table during the run. This guarantees your temporal queries can accurately filter out deleted entities.
