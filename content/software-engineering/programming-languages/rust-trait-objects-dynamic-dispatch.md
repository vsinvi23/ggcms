# Rust Trait Objects: Dynamic Dispatch, Vtables, and `Box<dyn Trait>`

By default, the Rust compiler prefers static dispatch when resolving trait methods. Through a process called **monomorphization**, the compiler generates a copy of the generic function for each concrete type that implements the trait. This results in zero-overhead, highly optimized execution, allowing the CPU to inline calls and predict branches efficiently.

However, static dispatch falls short when dealing with heterogeneous collections. If you need to store different types that implement the same trait inside a single array or vector — such as a list of various UI widgets that implement a `Draw` trait — monomorphization cannot help because the vector requires all its elements to have the exact same type and size at compile time.

To solve this, Rust provides **dynamic dispatch** using trait objects (`dyn Trait`). This article deconstructs how trait objects work under the hood, how the virtual table (vtable) is structured, and how to use `Box<dyn Trait>` to manage heterogeneous types at runtime.

---

## The Mental Model: Fat Pointers and Vtables

A regular reference in Rust (like `&MyStruct`) is a single pointer directly referencing the data on the heap or stack. In contrast, a trait object reference (like `&dyn Trait` or `Box<dyn Trait>`) is a **fat pointer**. It occupies exactly two words of memory:

1. **Data pointer**: a pointer to the concrete instance data.
2. **Vtable pointer**: a pointer to the virtual method table (vtable) generated by the compiler for that concrete type's trait implementation.

```text
       +------------------------------------+
       |   Box<dyn Trait> (Fat Pointer)     |
       +-----------------+------------------+
       |  Data Pointer   |  Vtable Pointer  |
       +--------+--------+--------+---------+
                |                 |
                v                 v
       +----------------+   +-------------------+
       | Concrete Data  |   |      Vtable       |
       |  e.g., Button  |   | - Type Metadata   |
       |  { width: 50 } |   | - size, alignment |
       +----------------+   | - drop_in_place() |
                            | - draw() pointer  |
                            +-------------------+
```

The vtable is constructed once at compile time and is shared among all trait objects of that concrete type. It contains essential metadata (like size, alignment, and the destructor pointer) alongside pointers to the actual implementations of the trait's methods.

## The Code: Static vs. Dynamic Dispatch

### The Static Approach (Monomorphization)

This approach is fast but requires compile-time knowledge of concrete types.

```rust
trait Draw {
    fn draw(&self);
}

struct Button { width: u32 }
impl Draw for Button {
    fn draw(&self) { println!("Drawing Button: {}", self.width); }
}

struct Label { text: String }
impl Draw for Label {
    fn draw(&self) { println!("Drawing Label: {}", self.text); }
}

// Compiler generates two separate functions under the hood
fn render_static<T: Draw>(item: T) {
    item.draw();
}
```

### The Dynamic Approach (Trait Objects)

This allows us to mix different types in a single collection.

```rust
// Using Box<dyn Draw> to represent a dynamic trait object
fn render_dynamic(items: Vec<Box<dyn Draw>>) {
    for item in items {
        // Method lookup happens at runtime via the vtable
        item.draw();
    }
}

fn main() {
    let mut components: Vec<Box<dyn Draw>> = Vec::new();

    components.push(Box::new(Button { width: 100 }));
    components.push(Box::new(Label { text: String::from("Submit") }));

    render_dynamic(components);
}
```

## Under the Hood: Object Safety and Memory

Because `dyn Trait` is unsized (marked `!Sized` in Rust), the compiler does not know its size at compile time. Consequently, you cannot store `dyn Trait` directly on the stack or pass it by value. It must always live behind a reference or smart pointer, such as `&dyn Trait`, `Box<dyn Trait>`, or `Rc<dyn Trait>`.

Furthermore, not all traits can be turned into trait objects. A trait must be **object safe**. This means:

- The trait must not require `Self: Sized` (since the trait object itself is unsized).
- All associated methods must not return `Self` and must not have generic type parameters.

If a trait violates object safety — for example, a `Clone`-like trait whose method returns `Self` — the compiler will reject any attempt to write `Box<dyn YourTrait>`, because the vtable has no way to represent "return a value of the caller's concrete type" for an erased type.

---

## Key Takeaways

- **Prefer static dispatch**: use generics and trait bounds by default. It allows the compiler to perform aggressive optimizations like function inlining and branch prediction, and it avoids the extra pointer indirection of a vtable lookup on every call.
- **Leverage dynamic dispatch for heterogeneity**: use `Box<dyn Trait>` when you must store different concrete types in a single collection or return different types from a function without an enum.
- **Watch for object safety**: ensure your traits do not return `Self` or use generic type parameters in their methods if you plan to use them as dynamic trait objects — otherwise the compiler will refuse to construct the vtable.
