# dbt Snapshots: Designing Type 2 Slowly Changing Dimensions

## The Overwritten History Problem

Transactional databases are optimized for real-time reads and writes. To save disk space and improve application performance, they overwrite data. When a customer changes their subscription plan from "Basic" to "Premium," or a product's price is updated, the database runs an `UPDATE` that permanently overwrites the old value.

In a data warehouse, this overwrite deletes vital context. If an analyst runs a historical report to evaluate customer churn or sales performance over the past fiscal year, they cannot reconstruct the pricing or plan states that existed at the exact moment of each transaction. Accurate historical audits and temporal analyses require **Type 2 Slowly Changing Dimensions (SCD Type 2)**, which track changes over time by creating new rows with valid start and end timestamps.

## Mental Model: Append-Only Temporal States

A dbt snapshot implements SCD Type 2 by querying a mutable source table at regular intervals, comparing the source data with the previously snapshotted table, and writing the differences as an append-only historical log.

```text
Source Table: (User 1, Plan='Basic')
           | (Updated to 'Premium' at 2026-06-01)
           v
Snapshot Table (SCD Type 2):
+----+------+---------+---------------------+---------------------+
| ID | User |  Plan   |   dbt_valid_from    |    dbt_valid_to     |
+----+------+---------+---------------------+---------------------+
| 1  | 1    | Basic   | 2026-05-01 00:00:00 | 2026-06-01 10:00:00 |
| 2  | 1    | Premium | 2026-06-01 10:00:00 | NULL                |
+----+------+---------+---------------------+---------------------+
```

The active record always carries `dbt_valid_to = NULL`, while past states carry the exact timestamp of their supersession.

## Snapshot Mechanics and Meta-Fields

To track changes, dbt adds several internal metadata fields to the snapshot table:

- `dbt_scd_id` — a unique primary key generated by hashing the source table's primary key and the record's modification time.
- `dbt_updated_at` — the timestamp when the record was last updated in the source table.
- `dbt_valid_from` — the timestamp when this historical version of the record became active.
- `dbt_valid_to` — the timestamp when this version was superseded; `NULL` for the active version.

### Two Change-Detection Strategies

1. **Timestamp strategy** — requires a reliable update timestamp column (e.g., `updated_at`) in the source table. dbt checks whether the source table's timestamp is newer than the `dbt_updated_at` stored in the snapshot. This is the most efficient strategy.
2. **Check strategy** — used when the source table lacks a reliable update timestamp. dbt computes a hash of a configured list of columns (or all columns via `check_cols = 'all'`) and compares it against the existing snapshot.

### Under the Hood: The Merge Statement

Running `dbt snapshot` compiles a `MERGE` statement (or an `INSERT`/`UPDATE` transaction, depending on the target warehouse). It left-joins the source table to the active rows of the existing snapshot table.

If a match is found and the change-detection strategy indicates the row changed:

- dbt updates the active snapshot record, setting `dbt_valid_to` to the snapshot execution runtime.
- dbt inserts a brand new row with the updated values, setting `dbt_valid_from` to the snapshot runtime and `dbt_valid_to` to `NULL`.

## Implementation Configuration

```sql
{% snapshot customer_accounts_snapshot %}

{{
    config(
      target_database='analytics_prod',
      target_schema='snapshots',
      unique_key='account_id',
      strategy='timestamp',
      updated_at='last_modified_date',
      invalidate_hard_deletes=True
    )
}}

SELECT
    account_id,
    customer_name,
    subscription_tier,
    billing_country,
    last_modified_date
FROM {{ source('crm_raw', 'accounts') }}

{% endsnapshot %}
```

Setting `invalidate_hard_deletes=True` makes dbt automatically update the `dbt_valid_to` field of any snapshot records that are completely missing from the source table during the run. This guarantees temporal queries can accurately filter out deleted entities, rather than treating them as still-active forever.

## Conclusion

dbt snapshots turn a mutable, overwrite-in-place source table into a durable, queryable SCD Type 2 history — without hand-rolling `MERGE` logic or metadata columns. Choosing `timestamp` strategy when a reliable `updated_at` exists (cheaper) versus `check` strategy when it doesn't (more thorough but costlier), and enabling `invalidate_hard_deletes` for tables where rows can disappear, are the two decisions that determine whether the resulting history is both efficient and correct.
