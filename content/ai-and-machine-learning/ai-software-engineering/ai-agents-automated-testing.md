# AI Agents for Automated Testing

> By the end of this article you'll be able to use an AI agent to generate, extend, and triage a test suite without fooling yourself about what those tests actually prove — and you'll know exactly which parts of this task an agent is genuinely good at versus which parts produce a green checkmark that means nothing.

## The Problem

Ask a coding agent to "write tests for this module" and it will not hesitate. Within seconds you get a `test_*.py` file with a dozen functions, each with a plausible name, each calling into your code, each asserting something. Coverage jumps from 40% to 95%. The CI badge turns green. Everyone moves on.

Here's the question that matters and that nobody asks in the moment: did those tests just prove your code works, or did they just prove your code does whatever your code does?

That distinction sounds pedantic until you sit with it. A test suite is only useful if it can fail — if there's some version of the code, some bug, some regression, that would make at least one assertion break. A test suite generated by reading the implementation and asserting "the function returns what the function returns" can never fail, because its expected value and its actual value come from the exact same source. It will pass today, and it will pass again after someone introduces a real bug next month, because the test was never checking behavior against an independent standard of correctness — it was checking the code against itself.

This is the central tension of this article. Generating *a* test is trivial for a model that can read code — it always was, template-based test scaffolding tools have existed for decades. Generating a test that would actually catch a real bug is a different problem entirely, and it's the one worth understanding before you wire an agent into your test pipeline.

## Two Different Jobs, Easy to Confuse

- **Testing AI agents** is about verifying the *agent's own behavior* — an inherently nondeterministic system that reasons, calls tools, and produces different outputs for the same input. That problem needs LLM-as-a-judge scoring and deterministic mocks precisely because you can't assert exact string equality on a model's reasoning.
- **AI agents *for* testing** (this article) is about using an agent as a *tool* to generate and maintain tests for ordinary, deterministic software — a REST handler, a pricing function, a data pipeline. The software under test behaves exactly the same way every time you run it. The hard part here isn't nondeterminism in what's being tested; it's that the thing writing the tests (the agent) has no independent knowledge of what the code is *supposed* to do, only what it *does* do.

These are genuinely different failure modes, and conflating them is why teams sometimes think "we already covered testing with agents" when they've only solved half of it.

## The Core Idea: What an Agent Can Actually Do Across the Test Lifecycle

Break "AI agents for testing" into the four jobs people actually mean when they say it, because each has a different risk profile:

1. **Test-case generation from code** — read a function or class and produce tests that exercise its branches.
2. **Test-case generation from a spec** — read an API contract, a ticket, or acceptance criteria, and produce tests that check the code *against that external description*, not against itself.
3. **Coverage-gap detection** — read a coverage report, find the untested branches, and target them specifically instead of generating tests at random.
4. **Flaky-test triage** — look at a test that sometimes passes and sometimes fails, and reason about why, without just papering over it.

Job 2 is structurally safer than Job 1, for a reason that matters enough to name now and come back to repeatedly: Job 2 gives the agent an oracle — a source of truth about correct behavior that is independent of the implementation. Job 1 does not. Keep that distinction in view; it's the thread running through everything below.

## How Test Generation Actually Works Under the Hood

An agent generating tests from code typically runs a loop like this:

```text
        Source File
             │
             ▼
   ┌────────────────────────┐   AST: functions, branches,
   │ 1. Parse structure      │   parameters, return types,
   │    (static analysis)    │   exceptions raised
   └────────────┬────────────┘
                ▼
   ┌────────────────────────┐   if/else branches, loop
   │ 2. Enumerate paths      │   boundaries, exception paths,
   │    to exercise          │   edge-case inputs (None, 0, -1, empty)
   └────────────┬────────────┘
                ▼
   ┌────────────────────────┐   Where does "expected value"
   │ 3. Draft assertions     │   come from? ← the fork in the road
   └────────────┬────────────┘
                │
       ┌────────┴─────────┐
       ▼                  ▼
  Run the function   Read a spec / ticket /
  and assert its      acceptance criteria and
  own output          assert against THAT
  (self-referential)  (independent oracle)
       │                  │
       ▼                  ▼
  Passes trivially,   Can actually fail if
  proves nothing new  the code is wrong
```

Step 1 and 2 are mechanical and genuinely reliable — static analysis of control flow to find branches, boundary values, and exception paths is a solved problem, and an LLM is a reasonable engine for enumerating "the interesting inputs" (empty collections, `null`/`None`, off-by-one boundaries, the largest and smallest representable values) because it's pattern-matching against a huge corpus of code that has already hit those edge cases.

Step 3 is where things fork, and the fork is invisible in the output. Both branches produce a file that looks like a normal test file. Only one of them can catch a bug.

### Property-based generation as a partial fix

One structural improvement worth knowing: instead of asking an agent to generate example-based tests (specific inputs, specific expected outputs), you can ask it to generate *properties* — invariants that should hold for a whole class of inputs — and hand those to a property-based testing library (Python's Hypothesis, JavaScript's fast-check, and similar tools in other ecosystems generate the actual example inputs and search for counterexamples).

```python
# Instead of the agent guessing specific example inputs...
def test_sort_example():
    assert sort_ascending([3, 1, 2]) == [1, 2, 3]

# ...ask it to state a PROPERTY that must hold for any input,
# and let a property-testing library search for a counterexample.
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_is_idempotent_and_ordered(xs):
    result = sort_ascending(xs)
    assert result == sorted(xs)              # matches a known-correct oracle
    assert sort_ascending(result) == result   # sorting twice changes nothing
    assert sorted(result) == result           # output really is non-decreasing
```

This doesn't solve the oracle problem on its own — `sorted(xs)` is doing the real correctness checking here, and for business logic there usually isn't a built-in function that already knows the right answer. But for a meaningful category of code (idempotence, sort order, round-trip serialization/deserialization, "output is a permutation of input," mathematical invariants like commutativity), the properties themselves *are* an independent, checkable description of correct behavior, which sidesteps the self-referential trap entirely.

## Let's Walk Through an Example

Take a small, realistic function: computing a loyalty discount.

```python
# pricing.py
def apply_loyalty_discount(subtotal: float, tier: str, years_active: int) -> float:
    if tier == "platinum":
        rate = 0.15
    elif tier == "gold":
        rate = 0.10
    else:
        rate = 0.0

    if years_active >= 5:
        rate += 0.02

    discount = round(subtotal * rate, 2)
    return round(subtotal - discount, 2)
```

**First pass — an agent given only this function, asked to "write tests":**

```python
# test_pricing_v1.py — generated from reading the implementation only
from pricing import apply_loyalty_discount

def test_platinum_discount():
    # Computed by tracing the function's own logic, not from a spec
    result = apply_loyalty_discount(100.0, "platinum", 2)
    assert result == 85.0

def test_gold_discount():
    result = apply_loyalty_discount(100.0, "gold", 2)
    assert result == 90.0

def test_unknown_tier():
    result = apply_loyalty_discount(100.0, "bronze", 2)
    assert result == 100.0
```

These tests will pass right now. But watch what happens with the actual danger case: a tier string that doesn't match any branch exactly — say, `"Platinum"` with capitalization — silently falls through to the `else` clause and gets treated as an unrecognized tier, with zero discount applied, and nothing here would tell you that's wrong. None of these three tests probes case sensitivity, the `years_active >= 5` boundary at exactly 5, or a negative `subtotal`. The agent picked three "happy path" values that exercise each branch once — which drives coverage to 100% of lines — while leaving the boundary conditions, the ones bugs actually hide in, completely unchecked.

**Second pass — run mutation testing against this suite** (deliberately introduce small bugs into `pricing.py` and check whether any test fails):

| Mutation | Does `test_pricing_v1.py` catch it? |
|---|---|
| Change `years_active >= 5` to `> 5` | **No** — no test uses `years_active == 5` |
| Change `tier == "platinum"` to `tier.lower() == "platinum"` (silently accepts case variants) | **No** — no test uses mismatched casing |
| Change `rate += 0.02` to `rate = 0.02` (overwrite instead of add) | **No** — no test combines a paying tier with `years_active >= 5` in a way that isolates the additive behavior |
| Change `round(subtotal - discount, 2)` to `round(subtotal + discount, 2)` | **Yes** — every existing test would fail |

Three out of four real mutations survive. 100% line coverage, and the suite would let three distinct bugs ship. This is the default outcome of asking an agent to generate tests from code alone without a mutation-testing gate, because "one input per branch" maximizes coverage percentage while doing nothing to probe boundaries.

**Third pass — a corrected suite**, generated by explicitly instructing the agent to target boundaries and combinations, and re-verified against the same mutations:

```python
# test_pricing_v2.py — boundary- and combination-aware
from pricing import apply_loyalty_discount

def test_years_active_boundary_at_five():
    below = apply_loyalty_discount(100.0, "gold", 4)
    at_boundary = apply_loyalty_discount(100.0, "gold", 5)
    assert below == 90.0          # no loyalty bonus yet
    assert at_boundary == 88.0    # 10% + 2% loyalty bonus applies exactly at 5

def test_tier_is_case_sensitive_by_current_contract():
    # Documents current (possibly surprising) behavior explicitly,
    # rather than assuming case doesn't matter
    assert apply_loyalty_discount(100.0, "Platinum", 2) == 100.0

def test_loyalty_bonus_is_additive_not_a_replacement():
    platinum_no_bonus = apply_loyalty_discount(100.0, "platinum", 1)
    platinum_with_bonus = apply_loyalty_discount(100.0, "platinum", 5)
    assert platinum_with_bonus < platinum_no_bonus  # bonus stacks with tier rate
    assert platinum_with_bonus == 83.0               # 15% + 2%, not just 2%
```

This suite catches all four mutations. Nothing about the code changed between the second and third pass — only the *thinking* behind what inputs to choose changed, from "one per branch" to "boundaries and interactions." An agent can be steered toward this if you ask for it explicitly (and better, if a mutation-testing gate rejects the weaker suite automatically) — but left to its own defaults, it optimizes for the metric it's told to optimize for, which is usually coverage percentage, not fault-detection strength.

## Coverage-Gap Detection: Where Agents Are Genuinely Strong

This is the job with the best return on investment, and it's worth understanding why: coverage-gap detection is fundamentally a *search* problem, not a *correctness judgment* problem, and search is exactly where mechanical tools plus an LLM's pattern recognition combine well.

```text
Coverage report (line/branch)
          │
          ▼
Find lines/branches with zero hits
          │
          ▼
Map each gap back to the specific
condition that would exercise it
(e.g., "the `else` on line 41 needs
 tier not in {platinum, gold}")
          │
          ▼
Generate ONE targeted test for
that specific gap
          │
          ▼
Re-run coverage → confirm the
gap closed → move to next gap
```

Because the target here is externally defined (a specific uncovered branch, visible in a coverage tool's output — not something the agent invents), this loop has a built-in success criterion that doesn't depend on the agent's judgment about correctness at all: did the previously-uncovered line get a hit, yes or no. That's a much safer job to hand an agent than "does this test verify the right behavior," because verifying "did this line execute" doesn't require an oracle — it's a fact about the run, not a claim about correctness.

The catch: closing a coverage gap only means the line *ran*. It says nothing about whether the assertion on that line checks anything meaningful — that's exactly the trap from the pricing example above, just relocated. Coverage-gap detection tells you *where* to add a test. It doesn't tell you whether the test you added there is any good — mutation testing is how you answer that.

## Flaky-Test Triage: Reasoning About Nondeterminism, Without Hiding It

A flaky test passes sometimes and fails other times, with no code change in between. Diagnosing it requires correlating failure logs, timing, and test order across many runs, which is exactly the kind of wide-context pattern-matching an agent can help with.

A reasonable triage loop:

1. **Confirm it's actually flaky, not a real intermittent bug in the code.** Re-run the failing test N times in isolation (same environment, same inputs). If it fails every time in isolation but passed in the original CI run, the *test* might not be the flaky thing — a shared fixture or run-order dependency might be.
2. **Classify the likely cause** by pattern-matching the failure signature against known categories:
   - **Timing/race conditions** — the test asserts something that depends on an operation finishing within an implicit, unstated deadline.
   - **Test-order or shared-state dependence** — passes alone, fails when run after test X, because test X leaves global state (a database row, a module-level cache, an environment variable) that this test implicitly depends on.
   - **External dependency instability** — the test calls a real network service, and the network, not the code, is what's flaky.
   - **Unseeded randomness or wall-clock dependence** — a `random.random()` or `datetime.now()` call without a fixed seed/clock, so behavior legitimately differs between runs.
3. **Propose a root cause with a confidence level and evidence** — "this test failed 4 times over the past 30 runs, always immediately after `test_bulk_import` ran, and both touch the same in-memory cache without resetting it between tests — likely order dependence" is a testable hypothesis an agent can generate from CI history that a human would have to dig for manually.
4. **Fix the actual cause, or quarantine with a tracked reason** — isolate the shared fixture, inject a fake clock, mock the external call, or add an explicit wait *on a specific condition* (not a fixed sleep). If the root cause can't be nailed down immediately, quarantine the test with an owner and a ticket — don't just leave it red-then-green-then-red in the main suite where it teaches the team to distrust CI.

**The anti-pattern to watch for, specifically because agents are prone to it:** given a flaky test and told "make CI pass," the fastest mechanical fix is adding a retry decorator or a longer `sleep()` before the assertion. This often "works" in the sense that CI turns green — and it's almost always the wrong fix, because it doesn't address the race condition, it just narrows the window in which the race loses. A retry that papers over a real concurrency bug in the *code under test* means a rare production failure now has zero visibility in CI, which is strictly worse than a visibly flaky test. Any agent-proposed fix that adds retries, sleeps, or increased timeouts without an accompanying explanation of *why* the underlying operation is racing should get exactly the scrutiny a human reviewer would give a suspiciously convenient one-line fix anywhere else.

## Where This Genuinely Improves Quality

The strong cases share a property: there's an external, checkable signal that doesn't depend on the agent's own judgment about correctness.

- **Coverage-gap closing against a coverage tool's report** — the target is externally defined and mechanically verifiable.
- **Boilerplate and table-driven test scaffolding** — parameterized tests across many similar input shapes, once a human has supplied one correct example and the expected pattern.
- **Contract tests generated from an API spec** (OpenAPI/JSON Schema) — the spec is the independent oracle; the test checks the implementation *against the spec*, not against itself.
- **Regression tests extracted from a bug report** — the bug report describes the *wrong* behavior and (usually) the expected fix; that's an oracle handed to the agent externally, not derived from reading the buggy code.
- **Characterization tests for legacy code** — notably, this is the one case where "assert what the code currently does" is the *correct* goal, not a trap, because the explicit purpose is capturing current behavior before a refactor, not verifying correctness.
- **Flaky-test root-cause hypotheses from CI history** — pattern-matching across many historical runs at a scale and speed a human triaging alone can't match, provided a human still approves the actual fix.

## Where It Produces Tests That Pass Without Testing Anything

### The oracle problem

State this plainly, because it's the idea everything else in this section hangs off: **a test is only meaningful if its expected result comes from a source of truth independent of the implementation being tested.** When an agent is handed only the source code and asked to write tests for it, the only "truth" available to derive expectations from *is* that source code. The agent can produce a test that is internally consistent — it will always pass, because the expected value was computed by the same logic being tested — but it cannot, by construction, produce a test that would fail if that logic is wrong, because "wrong" was never defined anywhere the agent could see it. This isn't a limitation of any particular model; it's a property of the task. No amount of model capability fixes a task that's missing an independent oracle.

### Concrete symptoms of the oracle problem

- **Tautological assertions.** `assert result == compute(input)` where `compute` is a copy or restatement of the function under test — the test can never fail.
- **Coverage-metric optimization over verification.** An agent instructed to "get coverage above 90%" will find the shortest path to that number: one input per branch, weak or absent assertions (`assert result is not None` instead of checking the actual value).
- **Snapshot/golden-master overreach.** Snapshot testing (capture the current full output, diff future runs against it) is legitimate for characterization work, but agents reach for it because it's mechanically easy to generate — call the function, serialize the output, assert equality forever after. Used as a *default* testing strategy rather than a deliberate choice, it locks in whatever the code currently does, bugs included, and worse: when a snapshot test fails after a real change, the path of least resistance is often to blindly regenerate the snapshot rather than investigate — silently absorbing a regression into the new "expected" baseline.
- **Self-grading.** An agent with write access to both the implementation and the test file can, when a test fails, "fix" the failure by editing the assertion to match the new (possibly wrong) output instead of investigating whether the code broke.

None of this means agent-generated tests are worthless. It means the value of any specific test the agent produces is bounded by whether an independent oracle was available when it was written — and that's a question worth asking about every agent-authored test file, not an occasional audit.

## Making It Work in Practice

- **Give the agent an oracle whenever one exists.** A ticket, an acceptance-criteria list, an API spec, a bug report, a product requirements doc — hand these to the agent alongside the code, and explicitly instruct it to assert against *that*, not against what the code currently returns.
- **Gate on mutation score, not coverage percentage.** Line and branch coverage answer "did this code run." Mutation testing answers "would a bug here get caught" — the question you actually care about. Run it, at minimum, on any file where an agent generated the majority of the test suite, and treat a low mutation score as a reason to reject the suite, not a curiosity.

  > **Verification Note**
  > Specific mutation-testing tools, their supported languages, and their default operator sets change over time and vary by ecosystem. Confirm current tooling against that tool's own documentation before adopting it in a CI pipeline.

- **Keep the test files and the fixtures/expected-values they assert against out of the agent's unrestricted write scope for automated re-runs.** If an agent can silently edit an assertion to make a failing test pass, "tests are green" stops being evidence of anything. A separate review step for any diff that touches both implementation and expected-output fixtures in the same change closes this gap.
- **Label characterization/golden-master tests distinctly from behavior tests** so nobody mistakes "this test proves the code hasn't changed" for "this test proves the code is correct."
- **Route agent-generated tests through the same CI sandboxing already used for agent-generated code changes.**

## Under the Hood: The Agent Loop Applied to Test Generation

Mapped onto the standard agent loop:

1. **Goal**: "Generate tests for `apply_loyalty_discount` targeting the uncovered branches in the latest coverage report, and assert against the pricing rules described in ticket PRICING-482, not just the function's current output."
2. **Context**: the function's source, the coverage report showing which lines/branches are unhit, and the ticket text describing intended tiering rules (the oracle).
3. **Reasoning/Planning**: identify which branches lack coverage, and for each, determine the input that exercises it *and* the expected value from the ticket's rules — not from re-running the function mentally.
4. **Tool Selection & Execution**: write the test file; run it in the sandbox.
5. **Observation**: capture pass/fail per test, and separately, the updated coverage percentage and (where wired in) the mutation score against a small mutant set for the touched file.
6. **Updated State**: if mutation score is low despite passing tests and full coverage, that's a signal to add boundary/combination cases — not a signal that the task is done.
7. **Next Action**: propose the new test file for human review rather than committing directly — the review here should specifically check what the assertions are checking, not just that the file exists and passes.

## Security Considerations

- **Running agent-generated tests is running agent-generated code.** A test file is executable code with the same blast radius as any other file the agent writes. It must run inside a sandboxed, resource-limited, network-restricted execution environment — never with elevated CI credentials just because "it's only a test."
- **An oracle handed to the agent is untrusted input, not just correctness data.** A ticket, bug report, or API spec fed to the agent as "the source of truth" can originate outside your trust boundary — a public issue tracker, a customer-submitted ticket, a third-party spec — and can contain text crafted to look like instructions rather than content to reason about. Treat oracle text as data to reason about, never as instructions to follow, regardless of how internal or trustworthy the source looks.
- **Agents inventing "realistic" test data can accidentally produce credential-shaped or PII-shaped strings.** An agent asked to generate sample records for a test fixture may synthesize plausible-looking API keys, emails, or ID numbers. Scan generated fixtures the same way you'd scan any other new file for secrets patterns, and prefer clearly-fake, clearly-labeled test data (`test-key-not-real`) over anything that could be mistaken for a live credential if it leaked.
- **New testing libraries pulled in by an agent are a dependency-upgrade risk, not a neutral dev-time convenience.** A mocking or property-testing library added to satisfy a test is still a new supply-chain dependency with its own transitive tree; treat it with the same scrutiny as any other dependency addition.
- **Test files that call real external services defeat sandbox isolation.** An agent generating "integration-style" tests may reach for the real database or a live third-party API to get a realistic assertion target, which both makes the test flaky and gives agent-run code a path outside the sandbox boundary. Require external calls to go through mocks or a designated test-double environment, enforced structurally, not just by instruction.

## Common Misconceptions

**Misconception:** "The agent generated tests and they all pass — the code is well tested now."
**Reality:** Passing tests only prove the tests don't contradict the current code. Whether they'd catch a *future* bug depends on whether they were checked against an independent oracle and validated with something like mutation testing. Coverage percentage measures execution, not verification.

**Misconception:** "An agent that writes tests can also be trusted to fix them when they fail."
**Reality:** An agent with write access to both implementation and test files can resolve a failure by editing either side. Letting it "fix" a failing test by changing the assertion is a self-grading failure — the fix needs to come from understanding *why* the output changed, and that judgment call belongs to a human when the two are entangled in one change.

**Misconception:** "A flaky test is a test problem, not a code problem."
**Reality:** Sometimes the test has a genuine bug (unseeded randomness, order dependence). Sometimes the flakiness is the *only visible symptom* of a real race condition in the code under test, and suppressing it with a retry removes the one signal that would have caught it before production.

## Real-World Architecture

Treat agent-driven test generation as its own pipeline stage, not an ad hoc prompt run by whoever's touching a file:

- **Coverage-gap sweeps as a scheduled job**, not a one-off: run coverage on the current main branch, have an agent target the top N uncovered branches, and open a PR per batch — reviewed like any other PR, never auto-merged, specifically because "coverage went up" is not the same claim as "the new tests are good."
- **Mutation testing as a merge gate on files an agent has substantially authored tests for**, distinct from (and in addition to) the coverage gate most pipelines already have.
- **A separate review lane for PRs that modify both implementation and test files in the same change** — this is the single highest-risk shape of diff described throughout this article, and it's cheap to flag mechanically (does this PR touch a `test_*` file and its corresponding source file together?) before a human ever opens it.
- **Quarantine tracking for flaky tests with an owner and expiry**, so agent-assisted triage has somewhere to route a test it can't confidently root-cause immediately, instead of the two failure modes teams default to: ignoring it forever, or deleting it.

## Expert Insight

The recurring lesson in practice is that the value of agent-generated tests tracks almost exactly with how well-specified the code already is — which is a strange, slightly humbling thing to discover, because it means the tool that was supposed to compensate for thin specs actually needs good specs to be useful in the first place. Handed a well-described API contract or a bug report with reproduction steps, an agent produces genuinely useful, oracle-backed tests fast. Handed a bare function with subtle, undocumented business logic and told to "write tests," it produces something that looks identical but is hollow — and the two are indistinguishable in a PR diff unless someone specifically checks what each assertion is comparing against.

The second lesson is about where to spend the review budget. Reviewing "does this test exist and does it pass" is nearly worthless as a review activity — the agent will always produce something that passes. Reviewing "what would have to be true about the code for this specific assertion to fail" is where the actual signal is. A test suite's job is to fail when something's wrong — everything else is decoration.

## Try It Yourself

**Goal**: Feel the difference between coverage and fault-detection firsthand.

**Starting Point**: Any small function with at least two branches and one boundary condition (a discount calculator, a validation function, a date-range check).

**Task**:
1. Ask an agent to "write tests" for the function, giving it only the source code — no spec, no ticket.
2. Check the resulting coverage percentage. It will likely be high.
3. Manually introduce three small mutations into the function: flip a comparison operator (`>=` to `>`), change a constant, and swap the order of two independent operations. Run the generated test suite after each mutation.
4. Count how many of the three mutations the suite actually catches.
5. Now go back and ask the agent to add tests specifically targeting boundary values and the combination of conditions your mutations touched. Re-run the mutation check.

**Expected Result**: The first pass will likely miss at least one mutation despite high coverage. The second pass, aimed explicitly at boundaries and combinations, should catch more of them with the same or only slightly higher line count.

**What You Learned**: Coverage percentage and fault-detection strength are correlated but far from the same thing, and the gap between them is exactly where a careless agent-generated test suite hides its weakest tests behind its strongest-looking metric.

## Pause and Think

An agent is given a function with no docstring, no ticket, no tests, and no spec — nothing but the code itself — and asked to generate a thorough test suite. Is there any way, in principle, for the resulting tests to verify *correctness* rather than merely *self-consistency* with the current implementation?

### Answer

No — not from that input alone. Correctness is a claim about whether the code matches an intended behavior, and intended behavior has to come from somewhere outside the code (a spec, a ticket, a human's stated intent, a mathematical property that's true independent of any particular implementation). Without one of those, the most a test can assert is "this is what the function currently returns," which is a legitimate and useful thing to capture — it's exactly what a characterization test is for — but it is not the same claim as "this is what the function is supposed to return." An agent (or a human, for that matter) faced with code-only input can produce excellent regression protection against *future* changes; it cannot produce evidence that the *current* behavior is right, because there was never an independent standard to check it against in the first place.

## Key Takeaways

- Using AI agents to test *your software* and using AI agents (or judges) to test *AI agents themselves* are different problems with different failure modes — don't assume covering one covers the other.
- The oracle problem is the central limitation: a test generated only from the implementation can be self-consistent but can never prove correctness, because its expected value and its actual value share the same source.
- Coverage-gap detection is the strongest use case, because the target (an unhit branch) is externally, mechanically defined — but closing a gap only proves a line ran, not that the assertion on it means anything.
- Mutation testing, not coverage percentage, is the honest measure of whether an agent-generated test suite would catch a real bug; treat a passing suite with a low mutation score as evidence of nothing.
- Flaky-test triage benefits from an agent's ability to pattern-match across historical CI runs, but watch specifically for the retry/sleep anti-pattern, which hides real race conditions instead of fixing them.
- Never let an agent hold unrestricted write access to both the implementation and the expected-value fixtures in the same change — that combination lets a "failing test" get resolved by editing the test instead of investigating the code.
