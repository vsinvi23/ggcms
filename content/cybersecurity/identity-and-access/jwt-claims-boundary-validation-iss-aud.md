# JWT Claim Validation: Enforcing Issuer (iss) and Audience (aud) Boundaries

## The Problem: The Cryptographic Verification Trap

A common security vulnerability in distributed APIs is the **Cryptographic Validation Trap**. Many engineers assume that if a JSON Web Token (JWT) passes signature verification successfully, the token is secure and the request is authenticated. This assumption is false.

Cryptographic validation only proves that the token was signed by a trusted private key. It does not prove:

1. **Intent**: Was the token meant for *this* specific microservice, or was it intercepted from a low-trust system?
2. **Context**: Is the token still valid, or was it issued for a different regional environment (e.g., staging vs. production)?
3. **Origin**: Was the token generated by the expected authorization authority, or was it issued by a secondary tenant sharing the same global key management service?

If a service fails to validate the **Issuer (`iss`)** and **Audience (`aud`)** claims, it becomes vulnerable to **Token Replay Attacks**. In this scenario, a valid token issued for a public-facing customer portal (e.g., `aud: "customer-spa"`) is extracted by an attacker and replayed to a high-security internal administration endpoint (e.g., expecting `aud: "admin-api"`). Because both APIs trust the same central Identity Provider (IdP) signature, the admin service accepts the token, giving the attacker unauthorized administrative access.

## Architectural Blueprint: The Claim Boundary Verification Pipeline

To secure access boundaries, token validation must proceed through a strict multi-stage pipeline. Signature verification is only the entry gate. The application must then validate the issuer bounds, target audience, and temporal claims against strict local assertions.

```
Incoming Request with Bearer Token
              |
              v
     +-----------------+
     |  Deconstruct    | ---> Extract Headers & Raw Claims
     +-----------------+
              |
              v
     +-----------------+
     | Verify Signature| ---> Check cryptographically against trusted JWKS
     +-----------------+
              |
              v
     +-----------------+
     | Verify Issuer   | ---> Assert 'iss' matches the local expected domain exactly
     +-----------------+
              |
              v
     +-----------------+
     | Verify Audience | ---> Assert 'aud' contains the local service identifier
     +-----------------+
              |
              v
     +-----------------+
     | Verify Temporal | ---> Check 'exp', 'nbf', and 'iat' boundaries (with clock skew)
     +-----------------+
              |
              v
   Access Granted / Authenticated Payload
```

## Attack Vectors

1. **The Confused Deputy (Cross-Service Replay)**: In this scenario, an attacker obtains a token minted for a low-privilege public client (e.g., a mobile companion app). They replay this token against a high-privilege backend administrative API. If the administrative API does not assert that `aud` matches its own identifier, it accepts the client's request.
2. **Cross-Tenant Authorization Bypass**: In SaaS environments using multi-tenant identity providers (like Azure AD or Auth0), multiple tenants share the same signing keys. If a service verifies the signature but fails to validate that the `iss` claim contains the exact tenant identifier (e.g., `https://login.example.com/tenant-123/`), a user from `tenant-456` can present their valid token to access `tenant-123` data.
3. **Algorithm Confusion (Key Substitution)**: Attackers alter the JWT header `alg` parameter from asymmetric (e.g., `RS256`) to symmetric (e.g., `HS256`), signing the token with the public key of the service. If the library doesn't strictly enforce algorithm constraints during validation, it will use the public key as an HMAC secret, validating the forged signature.

## Technical Implementation

Below is a robust TypeScript implementation for manual, strict claim validation. It handles complex multi-audience arrays, mitigates algorithm confusion, and enforces tight temporal bounds.

```typescript
import jwt from 'jsonwebtoken';

interface StrictValidationConfig {
  expectedIssuer: string;
  expectedAudience: string;
  allowedAlgorithms: string[];
  maxClockSkewSeconds: number;
}

export class JWTClaimsValidator {
  constructor(private config: StrictValidationConfig) {
    if (this.config.maxClockSkewSeconds < 0 || this.config.maxClockSkewSeconds > 300) {
      throw new Error('CONFIG_ERROR: Clock skew tolerance must be between 0 and 300 seconds');
    }
  }

  /**
   * Cryptographically validates signature and strictly checks claim boundaries
   */
  public validate(token: string, publicKey: string): jwt.JwtPayload {
    // 1. Force explicit cryptographic signature checks with correct algorithms
    let decoded: string | jwt.JwtPayload;
    try {
      decoded = jwt.verify(token, publicKey, {
        algorithms: this.config.allowedAlgorithms as jwt.Algorithm[],
        complete: false, // Return only payload for post-signature checks
      });
    } catch (err) {
      throw new Error(`SIGNATURE_VERIFICATION_FAILED: ${(err as Error).message}`);
    }

    if (typeof decoded === 'string' || !decoded) {
      throw new Error('INVALID_PAYLOAD: JWT payload is not a valid structured object');
    }

    const payload = decoded as jwt.JwtPayload;

    // 2. Validate Issuer Boundary (iss)
    if (!payload.iss) {
      throw new Error('BOUNDARY_VIOLATION: Missing issuer (iss) claim');
    }
    if (payload.iss !== this.config.expectedIssuer) {
      throw new Error(`BOUNDARY_VIOLATION: Issuer mismatch. Expected: ${this.config.expectedIssuer}, Found: ${payload.iss}`);
    }

    // 3. Validate Audience Boundary (aud)
    if (!payload.aud) {
      throw new Error('BOUNDARY_VIOLATION: Missing audience (aud) claim');
    }
    this.assertAudienceMatch(payload.aud, this.config.expectedAudience);

    // 4. Validate Temporal Bounds with strict clock skew handling
    const currentTime = Math.floor(Date.now() / 1000);
    const skew = this.config.maxClockSkewSeconds;

    // Validate Expiration (exp)
    if (!payload.exp) {
      throw new Error('BOUNDARY_VIOLATION: Missing expiration (exp) claim');
    }
    if (currentTime > payload.exp + skew) {
      throw new Error(`TEMPORAL_VIOLATION: Token has expired (expired at ${payload.exp})`);
    }

    // Validate Not Before (nbf)
    if (payload.nbf && payload.nbf > currentTime + skew) {
      throw new Error(`TEMPORAL_VIOLATION: Token is not yet active (active from ${payload.nbf})`);
    }

    // Validate Issued At (iat) to prevent tokens from the future
    if (payload.iat && payload.iat > currentTime + skew) {
      throw new Error(`TEMPORAL_VIOLATION: Token issued-at time lies in the future (issued at ${payload.iat})`);
    }

    return payload;
  }

  /**
   * Helper to handle both string and array-based audience claims
   */
  private assertAudienceMatch(tokenAud: string | string[], expectedAud: string): void {
    if (typeof tokenAud === 'string') {
      if (tokenAud !== expectedAud) {
        throw new Error(`BOUNDARY_VIOLATION: Audience mismatch. Expected: ${expectedAud}, Found: ${tokenAud}`);
      }
    } else if (Array.isArray(tokenAud)) {
      // In OIDC, an audience claim can be an array of strings. We ensure our service is explicitly contained.
      const hasMatch = tokenAud.includes(expectedAud);
      if (!hasMatch) {
        throw new Error(`BOUNDARY_VIOLATION: Audience mismatch. Expected entry "${expectedAud}" not found in list: ${JSON.stringify(tokenAud)}`);
      }
    } else {
      throw new Error('BOUNDARY_VIOLATION: Audience (aud) claim is in an invalid format');
    }
  }
}
```

### Wiring It Into a Request Handler

```typescript
const validator = new JWTClaimsValidator({
  expectedIssuer: 'https://auth.serenya.com/oauth/v2',
  expectedAudience: 'https://api.serenya.com/v1/payments',
  allowedAlgorithms: ['RS256'],
  maxClockSkewSeconds: 30,
});

app.use((req, res, next) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'missing_token' });

  try {
    req.claims = validator.validate(token, PUBLIC_SIGNING_KEY);
    next();
  } catch (err) {

  }
});
```

## Defensive Hardening Checklist

1. **Verify `iss` Domain Strictly**: Do not use sub-string matching or regex searches (e.g., `iss.includes("auth.com")`) to validate issuers. Perform exact, case-sensitive string equality checks.
2. **Prevent Replay with `aud` Checks**: Always assign a unique, specific audience ID (e.g., `https://api.domain.internal/v1/payments`) to each microservice. Do not share a generic global audience string (like `*` or `global-api`) across different business segments.
3. **Keep Clock Skew Minimal**: Limit clock tolerance to a maximum of 30-60 seconds. Allowing wide tolerances (e.g., 5+ minutes) increases the window of exposure for expired or stolen credentials.
4. **Never Disable Default Validation**: Always rely on established, maintained cryptographic libraries, and never bypass built-in validation routines with manual string parsing.
